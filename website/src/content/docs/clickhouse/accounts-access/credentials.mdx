---
title: Organizations and credentials
description: Separate ClickHouse Cloud deployment permissions from SQL application access.
---

An organization contains ClickHouse Cloud services. A management API key and
secret authorize resource changes; a SQL user and its grants authorize data
access. Supplying one credential does not authorize the other API.

## Select an organization

Pass `organizationId` on each resource. The deployment profile authenticates
requests; it does not choose a default organization. Create management keys
and assign their permissions in ClickHouse Cloud, not through this provider.

Follow [Setup](/clickhouse/setup) to store the key and secret privately.

## Separate SQL identities

Give deployment SQL users the DDL and system-table visibility required by
`SQL.Database`. Give applications only the grants their queries and inserts
need. `SQL.Connect` injects supplied credentials into an external host; it
creates no SQL user, role or grant.

A default database is not a permission boundary. A user with broader grants
can query or change other databases through the same connection.

## Protect secrets and state

Use [secret providers](/environments/secret-providers), including Doppler,
Infisical or per-stage secrets, for passwords. All code in a runtime can access
its injected SQL credentials. Keep Cloud management credentials out of runtimes.

Protect state backups: the initial service password cannot be read again from
ClickHouse, and adoption does not recover it. Never print that output.

See [SQL databases and connections](/clickhouse/services/sql) for the connection
binding and [Services](/clickhouse/services/service) for access lists and recovery.
